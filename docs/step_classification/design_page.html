What happens in one version

Only the second stage involves the LLM. Everything after it turns the rule into a score.

  1. export
    Builds the agent's read-only copy of the repo, with other lineages removed.
  2. agent
    Explores the data, writes the rule, keeps notes.
    rule · notes · scripts · transcript
  3. collect
    Copies the work back and commits it.
  4. sweep, fit, final
    Runs the rule over its parameter ranges, fits the landscape, reruns the best points.
    score
  5. summarize
    A separate skill sorts each rule into categories for the observation app.
    summary

Rule and notes, side by side

From pf-20261106-3. The rule shows a fine that scales with the rival's harshness. Only the notes say why.

Rule config · excerpt
params:
  thr:    contribution bar; shortfall below it is punished
  slope:  points per point of shortfall, vs a rival that never punishes
  alpha:  increase of slope per point of the rival's mean punishment
  m_dec:  multiplier in switch-decision rounds (3, 7, 11, 15, 19)
  t_stop: last round in which the manager punishes
code: |
  short  = th.clamp(thr - cn, min=0.0)
  scale  = slope * (1.0 + alpha * rival_p)
  is_dec = ((t % 4) == 3).float() * (t < 20).float()
  tf     = (m_dec * is_dec + (1.0 - is_dec)) * (t <= t_stop).float()
  punishment = scale[..., None] * short * tf
Notes · excerpts

Exploration 1. Logit of switching: own punishment +0.17/pt, the other group's mean punishment −0.20/pt. "A harsh rival manager pushes people toward us."

Exploration 5. A point of punishment returns about 0.26 pool next round: "break-even at best… punishment cannot be the main lever; membership is."

Exploration 6. Drafts the rule: scale enforcement by the rival's harshness, ease off in decision rounds, stop before the end.

This is why the pipeline codes the rule for what and the notes for what and why.

Steps

The output on the right of each step links to its format in Data formats.

  1. Open pass
    With no categories given, the LLM describes the mechanisms in a sample of rules, and extracts from the notes what the agent did and why.
    rule free codes · notes records
  2. What codebook, with a coverage check
    Cluster the rule codes into mechanisms. Then check whether the mechanisms found in the notes fit.
    what codebook
  3. Why codebook
    Cluster the reasons extracted from the notes.
    why codebook
  4. Expert review of both codebooks
    Field experts read the codebooks and comment on definitions, boundaries and theory links. No coding.
    codebooks final
  5. Apply
    One judge codes each rule, another codes each notes record. Every code carries a quote.
    rule codes · coded records
  6. Expert check after the fact
    Experts code rules that were not used to build the codebook. Their agreement with the LLM judge is reported.
    expert rule codes
  7. Join and analyse
    Codes joined with each version's score and its place in the lineage.
    analysis table

Principles

  • Open first, classify second. Rules and notes are first described in free text with quotes. Categories come afterwards and are applied to those descriptions.
  • Separate what from why. A mechanism and the reason for it are coded apart.
  • The what codebook comes from rules only. The notes can show that it is missing a mechanism some rule implements. Ideas that no rule implements are listed separately.
  • The reasons are stated reasons. The notes are the agent's own account.

What this could give us

  • From the rule codes, validated: which mechanisms the search converges on, and what a mechanism is worth when it enters a lineage.
  • From the notes codes, exploratory: which ideas were considered but not adopted, whether the code does what the notes claim, and which reasons go with which mechanisms.

Open

  • The rule sample. How many rules to free-code and how to draw them.
  • Granularity. How many mechanisms, and how fine.
  • How to classify reasons. One proposal: empirical (the agent ran an analysis), theoretical (what it knows about how people behave) and authoritative (it worked before). These may overlap. To be decided after the open pass.
  • Scope of the extraction. All notes, or a sample first.
  • The expert check. How many rules, how many raters, which agreement measure.

Notes records

The LLM reads a version's notes once and turns them into one record. The record lists the mechanisms the agent wrote about and, under each, the reasons it gave. Later steps add codes to the same record.

What a reason is. Anything the notes say about why the agent put a mechanism into the rule, or why it left one out. It is recorded in the agent's own terms, with the passage it comes from, and is not sorted into kinds at this point. A reason can be a result from the agent's own analysis, an expectation about how players behave, or the fact that something worked in an earlier version. A mechanism can have several reasons, or none when the notes give none. How reasons are sorted afterwards is an open question.

A mechanism with an empty what code is one the what codebook does not cover. That is the coverage check.

Codebook

The what codebook and the why codebook have the same shape: a list of categories.

name           short label, used as the code
definition     what counts and what does not
examples       one case that fits, one that does not
theory link    references
# illustrative: one entry of the what codebook
name:        rival-dependent fine
definition:  The size of the fine depends on how the other group's manager
             punishes. Fines that depend only on the own group do not count.
examples:
  fits:         pf-20261106-3, "scale = slope * (1.0 + alpha * rival_p)"
  does not fit: a rule whose fine depends only on the player's shortfall
theory link: (filled in when the codebook is written and reviewed)

The join

The analysis needs no format of its own. It combines the rule codes and the notes records by version and what code, and adds each version's parent and score from git.

Open

  • Level. Whether each mechanism in a notes record also says how far the idea got: considered, tested or adopted.
  • Shape of the why code. One category per reason, or several attributes. This depends on how reasons are classified.
  • In the code, or in use. Whether the join also records that a mechanism is switched off at the final parameters. This would come from the sweep.

What the surveys found

  • Corpus. 110 versions on 36 branches, each with a rule and notes. 107 have a final score. Three do not: two were never run and one failed.
  • Notes. All 110 follow the same four headings: Explorations, Key findings, Hypothesis, Justification.
  • Scores. The three campaigns use different units, so scores are only compared within a campaign.
  • Parent. Always the previous version of the same lineage. It is not recorded anywhere and is derived from the name. Some notes credit an older version for an idea, so the extraction records which version the notes name.
  • viper. Its GPU nodes are AMD. An inference setup that works there already exists in a sibling project, with a mid-sized model downloaded.
  • dais. A working job setup exists in a sibling project. It needs a newer inference version for the production model.

Changes to the design

The two goals for the final outcome (how ideas flow through the search, and how they relate to theory) need a little more than the data formats tab shows. The plan adds:

  • Status of each mechanism in the notes: adopted, rejected or considered, and whether an exploration tested it. This settles the open question about levels.
  • Theory named in the notes: any theory, concept or literature the agent mentions explicitly, with the passage.
  • Literature for the codebook: a separate file linking each category to publications. It is written by Claude with web search, because the model on the cluster has no web access.
